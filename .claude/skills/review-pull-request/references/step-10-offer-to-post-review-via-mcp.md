# Step 10 — Offer to Post Review (File + Line Comments)

After you show the report, ask:

> _"Should I post these findings as file + line comments on PR #[number]?"_

Post each finding as an **inline comment on an exact file and line**. Do **not** post a general PR-level or summary comment. Every comment must point to a file + line.

```markdown
Review Comments:

| File           | Line | Comment                                                                                        |
| -------------- | ---- | ---------------------------------------------------------------------------------------------- |
| `file.ts`      | 42   | "SRP violation: this function does too much. Need to refactor into smaller functions."         |
| `file.ts`      | 88   | "Avoid interpolating user input directly into SQL queries. Use parameterized queries instead." |
| `file.spec.ts` | 40   | "AAA violation: test name describes implementation details rather than behavior."              |
```

If a finding has no real file + line, skip it. Do not turn it into a general comment.

Do **not** add AI attribution to the comment. No "Generated by", "Reviewed by Claude", "Co-Authored-By: Claude", or similar lines. Each comment has only the finding.

## Posting via MCP

If the user says yes, use the MCP tool. Post each finding as a **line review comment** on its file and line. If the MCP can, post one **review** with all inline comments, not many separate comments. Never post a top-level PR comment.

## Posting via CLI

If you only have a CLI, post one inline comment per finding. Use the platform's API command. It needs the file path, the line, and (for GitHub) the head commit SHA.

**GitHub** — use the REST API through `gh` for line comments. Do **not** use plain `gh pr comment`. It posts a PR-level comment.

```bash
gh api repos/{owner}/{repo}/pulls/{number}/comments \
  -f body="<comment>" \
  -f commit_id="<head-sha>" \
  -f path="<file>" \
  -F line=<line> \
  -f side="RIGHT"
```

Get the head SHA with `gh pr view <number> --json headRefOid -q .headRefOid`.

**GitLab** — post a discussion on a diff line:

```bash
glab api projects/:id/merge_requests/<number>/discussions \
  -f body="<comment>" \
  -f "position[position_type]=text" \
  -f "position[new_path]=<file>" \
  -f "position[new_line]=<line>" \
  -f "position[base_sha]=<base-sha>" \
  -f "position[head_sha]=<head-sha>" \
  -f "position[start_sha]=<base-sha>"
```

**Bitbucket** — use the inline comment command of the installed CLI. Each CLI has different flags. The command must take a file path and a line number. If the CLI cannot comment on a file + line, do not post a general comment. Show the findings to the user in the table above instead.

## Posting via browser

If you only have a browser tool, open the **Files changed** tab (GitHub) or the **Changes** tab (GitLab, Bitbucket). For each finding:

1. Find the file and line.
2. Click the comment button on that line (e.g. the **+** icon).
3. Type the comment.
4. On GitHub, click **Start a review** for the first comment, then **Add review comment** for the rest. On other platforms, click the button that adds the line comment.

On GitHub, finish with **Finish your review** → **Comment**. Leave the summary box empty. Never choose **Approve** or **Request changes**, unless the user asks.

If you cannot comment on a line, do not post a general comment. Show that finding to the user in the table above.

After posting, tell the user how many inline comments you posted. Give the PR/MR link.
